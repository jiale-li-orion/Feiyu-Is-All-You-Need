# FatFish · 交互语义设计

**Interaction Semantics Specification**

上游：Product Behavior Specification、Information Architecture Specification。

## 0. 文档 Ownership

**本文定义 FatFish 各页面的交互行为及其预期反馈，是信息架构到组件与布局设计之间的行为层。**

信息架构已经确定页面拓扑、对象关系、信息归属与呈现优先级。本文沿用这些设计，进一步明确：

- 用户可以对页面中的信息和对象执行什么操作。
- 操作产生什么用户可感知的反馈。
- 操作如何继续、结束、中断，以及如何恢复。
- 不同页面之间如何保持交互连续性。

本文不负责决定组件形态、空间布局、视觉表现、动画和底层技术实现。后续可以结合成熟软件的交互范式与具体设计实践反向修订。

## 1. 首页与消息

### 1.1 大肥鱼首页（首屏）

应用默认进入大肥鱼主会话，作为用户与 FatFish 接触的首页。

用户应能直接开始交流、继续此前的对话，并从这里进入会话目录、事项和个人设置。

用户重新打开应用时，能够延续此前的交流。首屏应保持对当前对话的连续支持，不因后台任务变化而主动改变用户的交互焦点。

首屏具体展示内容、快捷操作、肥鱼角色表现及其空间组织，留待组件与布局设计阶段确定。

### 1.2 会话目录

用户可以在大肥鱼、通用肥鱼和专用肥鱼之间切换。

切换后进入对应的独立对话，保留各自的交流历史与草稿。

肥鱼主动向用户发送实际通讯时，用户能够感知新的消息，并更新相应会话的最近交互状态。后台事件不产生会话未读。

### 1.3 肥鱼交流

用户可以发送消息、追问、补充信息、停止当前回复，以及继续讨论。

肥鱼需要延续当前对话意图，避免要求用户重复已经明确的信息。

直接向专用肥鱼委派工作时，默认由该肥鱼交付结果；向大肥鱼委派跨软件工作时，由大肥鱼统一交付。

持续任务被后台受理后，用户可以离开当前会话继续交流。普通任务进度不自动变成聊天消息。

用户停止当前回复，不意味着已经受理的后台任务被取消。

### 1.4 查询与内容查看

用户通过自然语言提出查询，并在原会话中获得结果。

可以继续追问、要求展开历史、查看原始消息或打开文件。简单内容直接呈现，较长内容通过已有链接或查看能力访问。

从内容查看返回时，能够继续此前的对话，不丢失当前查询意图。

## 2. 事项

### 2.1 事项列表

用户进入事项页，查看「待我处理」和「正在推进」。

可以打开事项、返回列表，并继续此前的阅读位置。

后台普通进度变化应反映在对应事项中，不主动改变用户当前的浏览位置。

### 2.2 事项详情与操作

用户进入详情后，能够理解当前事务和下一步。

可以查看相关资料、历史和任务执行情况，并在必要时完成自己的决定。

根据事项实际状态，用户可以执行暂停、继续、取消或关闭等操作。

操作完成后，明确反馈是否生效，以及事项当前状态。查看详情、返回和刷新不应意外触发新的任务执行。

### 2.3 事项状态变化

用户能够区分正在推进、等待外部、需要自己处理、结果待核查和已经完成。

状态变化反映在原事项中。只有真正需要用户行动时，才进入待我处理。

事项完成后保留结果和历史，不要求用户重复确认已经完成的普通工作。

## 3. 我的与后台管理

### 3.1 个人设置

用户可以修改个性化偏好、软件连接与权限、自动化与通知、肥鱼小队、设备及外观设置。

修改后能够明确感知是否生效。失败时保留原有设置与操作上下文。

关闭通知不意味着停止后台工作；修改肥鱼外观不影响任务和通信。

### 3.2 后台与开发者 Dashboard

用户可以查看后台运行情况、自动化任务、Source、设备、Agent、模型、资源与诊断信息，并对允许管理的对象执行相应操作。

查看运行数据不需要唤醒大肥鱼进行语义推理。

从某项运行记录进入具体任务，再返回时能够恢复原来的管理位置。关闭 Dashboard 不影响后台工作。

## 4. 跨页面交互连续性

以下路径需要在不同页面之间保持一致的交互体验：

| 操作路径 | 预期行为 |
|---|---|
| 首页 → 会话目录 → 专用肥鱼 → 返回 | 保持会话身份与原有交流上下文 |
| 大肥鱼 → 委派任务 → 事项 | 工作已受理，可以继续其他交流；事项能够找到对应工作 |
| 专用肥鱼 → 处理工作 → 返回主会话 | 领域工作继续存在，不要求复制全部内部交流 |
| 主会话 → 查询结果 → 查看原文 → 返回 | 保留查询意图与原会话位置 |
| 事项 → 授权 → 返回 | 授权结果在相关事项与会话中保持一致 |
| 事项 → 执行记录 → 返回 | 恢复原事项的查看位置 |
| 我的 → 账号授权 → 返回 | 保留原设置或任务上下文 |
| Dashboard → 运行记录 → 具体任务 → 返回 | 业务状态更新，但不丢失原管理位置 |

同一工作在多个页面出现时，用户执行一次操作即可改变对应业务状态，不产生重复操作或重复通讯。

## 5. 中断与异常反馈

| 场景 | 预期交互反馈 |
|---|---|
| 消息提交尚未确认 | 保留原文，明确当前提交结果未知 |
| 肥鱼回复中断 | 保留已有回复，允许继续交流 |
| 当前查询部分来源不可用 | 保留已取得的结果，说明受影响范围 |
| 后台任务暂时阻塞 | 在原事项中说明等待条件 |
| 外部操作结果不确定 | 在原任务中保留待核查状态 |
| 软件账号需要重新授权 | 提供对应账号的恢复入口 |
| 需要用户亲自完成操作 | 在原事项中明确下一步 |
| 授权对象或内容已经变化 | 更新当前状态，不能继续执行失效操作 |
| 应用暂时不可用 | 保留可用内容，说明恢复后的继续方式 |

异常首先在原操作上下文中反馈。只有需要用户完成独立恢复操作时，才进入相应的账号、事项或管理页面。

这里定义的是用户需要感知的异常及恢复行为，不规定底层重试、任务恢复或故障处理算法，也不要求每种异常拥有独立页面。

## 6. 向后续设计交付

本文向下一阶段提供：

- 各页面的用户操作集合。
- 操作的前后关系与跨页面路径。
- 用户能够感知的反馈与状态变化。
- 中断、异常和恢复时需要支持的行为。

**组件与布局设计**负责将这些行为映射为具体的组件、空间组织、操作入口和 PC / 手机布局。

**视觉与动效设计**负责建立操作反馈的视觉表达、信息层级、运动连续性与角色表现。

具体控件、页面形式和交互细节允许在后续设计中
