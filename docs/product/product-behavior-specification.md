# FatFish · 产品行为规范

**Product Behavior Specification**

---

## 0. 产品定义

FatFish 是一个持续运行、跨软件、跨设备的私人 Agent 系统。

用户通过一个长期主会话与「大肥鱼」交流。后台的专用肥鱼负责观察、理解和操作各自的软件，Super-agent 负责事务与任务的生命周期，Meshfin 负责现有跨设备通信，PC 和 Android 提供实际执行环境。

系统的目标是尽可能减少用户亲自打开软件、检查消息、组织任务、监督执行和恢复中断工作的次数。

### 0.1 产品成功的定义

用户可以长时间不打开 QQ、微信、飞书等应用，仍然能够通过大肥鱼掌握重要事务、完成已授权的操作，并且知道系统在哪些软件和时间段可能遗漏了信息。

系统新增软件或 Worker 时，不应要求用户投入等比例增加的管理精力。

### 0.2 已确定的产品边界

| 问题 | 行为决策 |
|---|---|
| 用户与谁交流 | 一个大肥鱼长期主会话，专用肥鱼可以按需进入 |
| 软件账号 | 优先操作用户已经拥有、已经登录并授权的真实账号 |
| 机器人身份 | 不以额外 Bot 联系人作为主要软件接入方式 |
| 软件分工 | 每个 Source 具有确定的负责肥鱼；跨软件事务统一协调 |
| Agent 运行 | 逻辑身份长期存在，实际模型 Session 按需创建 |
| 设备通信 | 复用已经打通的 Meshfin |
| 软件操作 | 现成 CLI/API 优先，GUI 负责补充和兜底 |
| 任务所有权 | 由 Super-agent 持久维护，独立于模型 Session 和执行设备 |
| 主会话上下文 | 保留重要认知与事务演化，原始社交消息按需读取 |
| 外部写入 | 根据用户授予的操作权限执行，保留核查与审计 |
| 软件故障 | 显式记录信息缺口、执行中断和结果不确定性 |
| 用户注意力 | 普通事务自主处理，重要变化集中汇报，必要决策即时请求 |

## 1. Agent 角色与责任

### 1.1 大肥鱼

大肥鱼是唯一全局主 Agent，负责：

- 理解用户的长期目标、偏好与当前意图。
- 维护跨平台事务及其相互依赖。
- 协调软件专用肥鱼与通用肥鱼。
- 判断何时需要用户注意。
- 统一接收任务结果、异常和授权请求。
- 维护长期主会话的认知连续性。

大肥鱼默认不消费每一条软件原始消息，也不需要亲自执行每个工具调用。

用户可以随时要求大肥鱼进入某项事务的细节，或者让它直接委派某个专用肥鱼处理工作。

### 1.2 专用肥鱼

每个专用肥鱼具有稳定的逻辑身份和职责范围。

例如，QQ 肥鱼负责个人 QQ 的消息变化、聊天历史、联系人、群组和可执行操作；微信肥鱼负责个人微信及有关小程序；飞书肥鱼负责飞书消息、文档、审批和业务任务。

专用肥鱼拥有软件领域状态，包括：

- 已发现的消息与事件。
- 对应软件的账号和会话标识。
- 已读取的上下文、增量游标和已知缺口。
- 正在负责或等待恢复的事务。
- 可用的 CLI、API、GUI Provider。
- 设备可用性和能力限制。

它们能够在自己已获授权的职责范围内自主处理普通事务。

专用肥鱼可以直接与用户交流，但其重要结论、外部承诺和授权变更仍应更新统一的全局事务状态。

### 1.3 通用肥鱼

通用肥鱼处理尚无专用负责人或跨越一般软件能力的任务。

它负责通用 Browser Use、Desktop GUI、Mobile Use 等工具的使用与调度。

通用肥鱼不因掌握 GUI 能力而自动获得任何账号的全部操作权限。

当某个通用任务反复出现且形成稳定的软件语义时，可以将其能力沉淀为专用 CLI，并交由对应专用肥鱼维护。

### 1.4 逻辑 Agent 与运行 Session 分离

一个专用肥鱼长期存在，不要求一个 LLM Session 永远运行。

用户可在任何时间联系它。收到事件或 Assignment 时，系统按需恢复或创建运行 Session，加载所属软件与事务的必要上下文，执行完成后释放运行资源。

Session 的关闭、压缩或迁移不能使软件负责关系、任务状态和长期事项消失。

## 2. 软件信息的观察行为

### 2.1 软件接入

用户授权一个软件账号后，系统应首先检查其真实可用能力，包括：

- 能否接收实时消息或事件。
- 能否查询已有消息及历史。
- 能否读取会话、联系人、附件和业务对象。
- 能否执行读写操作。
- 能否验证外部操作结果。
- 能否在设备离线后补收遗漏信息。

每项能力单独标记可用性和覆盖范围。

「连接成功」只代表当前 Provider 已建立连接，不代表该软件已经实现完整的信息观察或操作能力。

### 2.2 新信息进入系统

当软件产生新消息或事件时：

1. Source 接收并记录原始事件、来源、时间和稳定标识。
2. 检查重复接收和已知同步游标。
3. 判断事件属于哪个软件、账号、会话及负责肥鱼。
4. 查询是否关联已有事务或已授权任务。
5. 专用肥鱼根据上下文判断事件的实际意义。
6. 需要行动时推进已有任务或提出新任务候选。
7. 仅在满足注意力规则时向大肥鱼汇报。

普通消息不必为每条创建 Ticket，也不必每条都触发一次完整的模型推理。

系统可以批量处理、合并事件，或在需要更多上下文时再调用模型。

### 2.3 消息与任务的区分

收到一条消息，不自动意味着用户产生了一项任务。

外部联系人提出请求，只构成一条待评估的信息。它是否成为用户的任务，取决于用户目标、已有承诺、上下文及授权规则。

例如，群里有人讨论会议时间，默认属于普通信息；明确要求用户提交材料时，可能形成待办；若涉及用户此前已授权跟进的事项，则可以直接推进该事务。

外部聊天内容不能直接授予 Agent 新权限，也不能仅凭文本命令要求 Agent 操作其他软件或读取敏感资料。

### 2.4 信息覆盖范围

每个 Source 应持续记录当前信息覆盖情况。

状态至少区分：

- 正常同步：在已声明的范围内持续接收或成功查询。
- 部分可见：例如只有通知预览、特定群或特定账号数据。
- 同步滞后：读取游标落后于当前时间。
- 暂时断开：Provider 或设备不可用。
- 缺口待核查：某个时间段没有可靠的数据覆盖。

**未发现新消息，不代表软件中一定没有新消息。**

在回答「今天还有谁找我」时，系统应按可用来源检索，并说明明显缺失的时间段或软件，而不能把未知结果报告成全部检查完毕。

### 2.5 历史补收

软件恢复连接后，应根据其能力进行增量补收。

可读取稳定历史的 Provider 优先使用历史接口；只能读取当前界面的软件，通过通知索引或按需 GUI 检查辅助恢复。

补收过程中保留原始时间，避免将旧消息误认为刚发生的新事件。

对于无法恢复的历史，保留明确的缺口记录，而非自动推测内容。

## 3. 跨软件事务行为

### 3.1 Case：持续存在的事项

FatFish 使用 Case 表示一个可能跨越多个消息、软件和任务的用户事务。

Case 记录目标、参与者、重要证据、当前状态、待完成动作和后续依赖。

例如：

某人在 QQ 中提出合作，随后通过飞书提供文件，最终要求用户在微信小程序完成登记。这三类信息应在证据充分时关联为同一个 Case。

一个 Case 可以包含多个 Super-agent Ticket。

Case 负责事务连续性；Ticket 负责被授权的具体工作及执行生命周期。

Case 不独立实现第二套任务调度器。

### 3.2 Case 的创建

遇到新信息时优先检查是否属于已有 Case。

如果缺乏明确的行动需求，可以保留为可检索信息，不立即创建 Case。

只有存在实际目标、承诺、待跟进状态或明确用户关注时，才将它提升为持续事项。

关联证据不足时可以保留候选关系；不能因为两个平台的联系人名称相似，就断定它们属于同一个人或事务。

### 3.3 Case 的持续状态

用户主要看到以下事务状态：

| 状态 | 行为 |
|---|---|
| 待处理 | 已识别需要行动，尚未开始 |
| 处理中 | 有 Agent / Worker 正在推进 |
| 等待外部 | 已发出请求，等待其他人或系统变化 |
| 等待用户 | 缺少授权、信息或决策 |
| 暂时阻塞 | 工具、权限、设备或信息不足 |
| 已完成 | 完成条件经必要验证 |
| 已关闭 | 用户明确不再跟进，或事项被撤销 |

执行失败与任务暂停不自动代表 Case 已结束。

已完成事项收到相关后续事件时，可以依据原始事务目标重新打开或建立后续 Case。

### 3.4 任务拆分与归属

当一个 Case 涉及多个软件时，大肥鱼根据目标、依赖和权限将工作交给相应专用肥鱼。

任务来源决定初始负责者，操作对象决定具体执行者。

例如 QQ 肥鱼识别一项飞书审批需求，可以把操作交给飞书肥鱼。QQ 肥鱼仍维护原始消息及来源证据，大肥鱼维护跨平台事务状态。

任务移交不自动扩大接受方对原始聊天或其他账号数据的读取权限。

### 3.5 承诺管理

系统需要区分以下关系：

- 用户自己承诺完成的工作。
- 外部联系人承诺向用户交付的结果。
- Agent 已获得授权、承诺替用户推进的工作。
- 尚未被接受的外部请求。

承诺可以具有期限、条件、依赖和责任主体。

当用户说「我明天再处理」，系统更新事项的等待或提醒状态，不将其标记为完成。

当外部承诺到期而未满足时，可以按用户规则检查进展、准备催办或向用户汇报。

## 4. 软件操作行为

### 4.1 统一操作语义

专用肥鱼通过四类能力与软件交互：

**Observe**：持续发现变化。

**Read**：读取当前状态和必要历史。

**Act**：执行用户授权的动作。

**Verify**：验证动作是否在目标软件中生效。

软件操作优先选择稳定的原生 CLI、现有 API 或社区 Provider。能力不足时，由 BrowserSkill、DSH Go 或 Desktop GUI 执行。

同一软件可以同时拥有多个 Provider，读写与验证也允许使用不同 Provider。

### 4.2 执行前检查

实际执行操作之前，需要确认：

- 目标账号和对象正确。
- 操作仍在任务授权范围内。
- 设备与 Provider 当前可用。
- 目标软件状态仍满足操作前置条件。
- 是否已经执行过相同动作。
- 此动作是否需要用户确认。

对于会产生外部影响的操作，这些检查比简单的工具可用性更重要。

### 4.3 执行结果

外部动作采用以下基本结果语义：

| 状态 | 含义 |
|---|---|
| 已准备 | 操作参数和目标已经确定 |
| 已授权 | 得到必要授权，尚未执行 |
| 已尝试 | 操作请求已提交或已触发 GUI |
| 核查中 | 正在确认目标软件实际状态 |
| 已完成 | 已获得足够的完成证据 |
| 结果不确定 | 无法可靠判断外部动作是否成功 |
| 未完成 | 有证据表明执行失败或被拒绝 |

CLI 返回成功只是一种证据；对重要外部动作，应尽可能验证目标状态。

### 4.4 写操作与授权

FatFish 的权限按影响范围划分，而不是简单按软件划分。

| 操作类型 | 初始默认行为 |
|---|---|
| 已授权数据的读取、搜索与整理 | 自主执行 |
| 生成草稿、分类、准备材料 | 自主执行 |
| 授权范围内的低风险、可恢复操作 | 可以按预授权规则自动执行 |
| 向第三方发送消息、提交表单或建立承诺 | 初始要求确认；可按联系人、软件、动作建立预授权 |
| 付款、敏感信息披露、重要审批和不可逆删除 | 单次显式确认或本人接管 |

用户可以设置特定联系人、群组、任务类型或软件的自动化权限。

一次授权应明确作用范围，避免用户为了同一项已授权工作反复确认。

外部消息不能改变这些授权规则。

### 4.5 结果不确定与防重复

对于消息发送、表单提交等操作，网络超时和设备断连不能直接解释为动作未生效。

系统应先检查目标软件当前状态。

在完成状态核查前，不自动重放可能导致重复副作用的动作。

如果目标系统无法提供可靠结果，保持「结果不确定」，并在必要时请求用户核查。

### 4.6 GUI 执行

GUI Provider 执行前观察当前界面，确认目标软件、账号和操作对象。

执行过程中可以根据界面变化调整步骤，但不能绕过用户权限或安全限制。

设备失去连接后，恢复时重新观察界面和目标状态，再决定继续、重做安全步骤或请求人工处理。

同一设备的前台交互资源由统一管理器协调，避免不同肥鱼同时操作同一个屏幕。

## 5. 自主处理与主动跟进

### 5.1 两类任务来源

**用户主动委派**：用户明确提出目标，由大肥鱼或专用肥鱼创建任务，并在授权范围内执行。

**系统主动发现**：Source、定时条件或外部状态变化产生事件，由既有规则决定是否形成任务候选。

主动发现不等于无限自主授权。新任务的实际执行范围仍由用户策略控制。

### 5.2 自主跟进

系统能够跟进等待中的外部依赖，例如：

- 已发送但尚未回复的重要消息。
- 距离期限较近的报名或提交。
- 等待他人提供的资料。
- 需要确认是否完成的跨平台操作。
- 长时间没有进展的已授权事项。

跟进频率受事项重要性、截止时间、已有提醒记录及用户偏好约束。

当新的检查不会改变当前判断时，系统应避免无意义地重复查询或提醒。

### 5.3 任务取消与暂停

用户可以明确停止一个 Ticket、暂停一个 Case、关闭某软件的自动化，或停止全部当前自主执行。

停止任务不能撤销已经在外部发生的副作用。

系统应区分「禁止继续执行」和「撤销已完成操作」，必要时提供可执行的补救方案。

暂停不删除任务历史和证据。

## 6. 大肥鱼与用户的通信

### 6.1 唯一主会话

用户在 PC、Android 等不同设备上看到相同的逻辑主会话。

主会话保存用户的目标、重要决策、事务上下文与交互历史；它不依附于单台设备或某次推理进程。

专用肥鱼的会话是可选择的深入入口，不作为接收普通消息的必要路径。

### 6.2 统一的 Agent-Human 通信

所有 Agent 的人类通信统一采用以下目的：

- **Question**：需要用户补充事实或作出判断。
- **Approval**：请求授权执行特定动作。
- **Notice**：有价值但不需要即时决定的变化。
- **Result**：完成、失败或结果不确定的报告。
- **Digest**：集中整理一段时间内值得关注的事项。

每条通信关联对应 Case、Ticket 和证据来源。

同一事务的多个 Agent 不应各自反复通知用户。

用户可以在专用肥鱼会话中响应问题，但全局待处理记录保持一致。

### 6.3 注意力分配

系统默认将事件分为三个用户注意力等级。

**静默**：普通消息、重复通知、可自主处理的工作。不要求用户感知。

**集中摘要**：有价值但暂不紧急的事项，进入统一事务摘要。

**即时请求**：需要用户决策、存在明确时间风险，或者必须由用户亲自完成的动作。

是否即时打扰需要综合考虑影响、时限、可逆性、信息确定性和用户当前可用性。

不能仅因为一条消息包含「紧急」「重要」等字样，就提高打断等级。

### 6.4 主会话的报告要求

汇报以决策和结果为优先。

大肥鱼说明：

1. 发生了什么实质变化。
2. 当前已经处理到什么程度。
3. 哪些结论有证据支持。
4. 如果需要用户行动，用户具体需要决定什么。

默认不展示完整工具日志、原始事件流或所有 Worker 的中间输出。

用户要求深入时，应能够逐层展开证据和执行过程。

### 6.5 及时沟通与沉默

已经开始的普通后台工作，不需要持续发送「正在进行中」的通知。

重要结果、需要用户协助的障碍及异常仍需及时报告。

用户正在主会话中讨论其他问题时，后台任务继续运行，不应通过重复插话夺取对话焦点。

## 7. 搜索、查询与历史

### 7.1 跨软件查询

用户可以直接通过大肥鱼查询：

- 谁最近联系过自己。
- 某件事在不同软件中的进展。
- 哪些承诺尚未完成。
- 某人此前提供过哪些资料。
- 某项操作是否真的提交成功。

系统按账号授权和信息可用范围进行检索，并返回可追溯的来源证据。

### 7.2 跨平台身份关联

同一个人在不同平台的账号可以建立关联，但关联需要证据。

相同昵称、头像、话题只能提供候选线索。

跨平台身份关联主要用于检索和事务理解，不自动传播平台账号的权限。

对于未确认身份，系统保留原生账号标识，避免错误合并联系人及错误发送信息。

### 7.3 原始信息与长期记忆

原始消息、事件和附件尽可能保留来源索引。

从这些信息中提取的长期记忆必须能够回溯到证据，同时区分事实、推断、偏好和未确认信息。

专用肥鱼保留软件领域状态；大肥鱼只接收影响全局目标和事务判断的重要变化。

主 Agent 的长期认知还需要保留关键判断依据和问题演化过程，不能完全依赖短字段摘要重新推理。

## 8. 跨设备与离线行为

### 8.1 设备独立

PC、手机和其他 Meshfin 节点分别登记可用能力。

用户不需要为了使用大肥鱼而一直开启某一台指定设备。

当设备下线时：

- 可由其他节点完成的工作继续执行。
- 只能在该设备完成的工作进入等待。
- 任务与事务状态仍然保留。
- 如果下线影响软件消息观察，记录相应信息缺口。

### 8.2 主会话恢复

逻辑上只有一个主会话，可以由不同运行节点承载。

系统恢复主会话时，优先恢复已确认的用户决策、未完成事务和相关上下文。

需要避免多个节点同时执行相互冲突的主控写入。

如果没有任何可用计算节点或常驻服务，系统无法继续实时处理新事件；恢复后应明确说明离线时间及可补收范围。

Meshfin 已有通信能力直接复用，主控执行所有权及权威状态同步仍需通过集成测试验证。

### 8.3 Worker 恢复

Worker 中断后，Ticket 保留，Assignment 可以恢复或重新分配。

对于只读或明确幂等的操作，可以按策略恢复。

对于存在外部副作用的操作，应先核查结果。

恢复行为不能仅由「超时」触发无条件重试。

### 8.4 模型不可用

模型调用失败时，Source 继续保存其已经收到的事件；无需模型即可完成的确定性处理可以继续。

需要模型判断的事务等待恢复。

恢复后优先处理时间敏感的积压事项，并向用户报告具有实际影响的遗漏或延迟。

## 9. 权限、隐私与用户控制

### 9.1 账号授权

用户按软件和账号授权接入能力。

读取历史、发送消息、执行 GUI 和访问敏感资料应具有独立权限边界。

第三方账号工具尽量在实际登录设备上持有凭据，不把原始账号密码分发给多个 Agent。

### 9.2 外部信息可信度

来自 QQ、微信、网页、附件等外部来源的内容属于待理解的数据。

其中出现的命令、提示词或伪装系统指令，不具备修改 Agent 权限和行为策略的效力。

当用户请求基于外部资料执行动作时，执行授权来自用户或已有 Policy。

### 9.3 用户可控能力

用户可以：

- 查看哪些软件账号已被接入。
- 查询各软件的读取覆盖范围。
- 暂停某个 Source 或专用肥鱼。
- 修改自动化权限与通知策略。
- 检查 Agent 已执行的外部动作。
- 关闭、取消或恢复某个事务。
- 更正跨平台身份与事务关联。
- 撤销账号权限、移除连接或删除相应数据。

暂停自动化不等于必须删除历史；撤销账号连接与清除历史应分别提供明确语义。

## 10. 典型行为场景

### 场景 A：普通 QQ 群聊

群里连续产生大量消息。

QQ 肥鱼记录可观察范围内的事件，批量分析相关内容。大部分消息不形成 Case，也不通知用户。

有人明确提出与用户已有合作有关的新要求时，QQ 肥鱼将证据关联到现有 Case。

如果没有改变用户判断或任务安排，仍然静默处理；发生重要变化时，才更新大肥鱼的事务摘要。

### 场景 B：跨软件办理事务

用户让大肥鱼处理一个需要飞书文件和微信小程序共同完成的事项。

大肥鱼确定目标和必要授权，形成 Case。

飞书肥鱼获取文件并完成相关资料准备；微信肥鱼根据现有能力选择 API 或 DSH Go GUI，完成后核查小程序状态。

大肥鱼只呈现完整事务的结果，除非中途需要用户确认。

### 场景 C：个人微信电脑端离线

PC 关机，WeFlow 不再提供 Windows 微信增量读取。

微信肥鱼保留该 Source 的同步水位线，并记录信息缺口。

如果手机有相应通知或可用 GUI，可以辅助观察重要会话。

PC 恢复后进行历史补收，合并重复消息，重新评估遗漏期间发生的重要事务。

不能在未核查的情况下声称离线期间所有微信消息均已处理。

### 场景 D：消息发送结果不确定

微信肥鱼在授权后发送回复，操作期间设备断线。

Super-agent 保留 Ticket，不直接创建一次新的发送动作。

恢复时先通过可用的聊天历史或 GUI 检查消息是否已经出现。

核查成功则报告完成；无法确认则标记不确定，并根据风险决定是否请求用户介入。

### 场景 E：用户暂时不处理

用户对大肥鱼说：「这件事先放着，明天再说。」

Case 保留原有证据与任务状态，进入等待用户的状态。

已有外部执行根据用户表达暂停或继续，不自动把「明天再说」解释为撤销全部任务。

约定时间到达后，系统重新呈现必要信息，避免让用户重新阅读完整历史才能恢复判断。

### 场景 F：用户主动探索

用户问：「最近 QQ、微信、飞书里有什么和实习有关的事？」

大肥鱼检索各软件肥鱼维护的事件及事项，必要时调用 Provider 补充信息。

回复按事务组织，并提供来源证据。对信息缺失的软件标明当前覆盖限制。

用户可以继续追问某项事务的完整经过，而无须知道它最初出现在哪个软件。

## 11. 产品行为验收

以下验收条件在设计和实现阶段保持稳定。

| 编号 | 可验证条件 | 预期结果 |
|---|---|---|
| B01 | 同一条消息被重复接收 | 不重复形成事务或外部动作 |
| B02 | 大量无关群聊事件进入系统 | 不线性增加用户通知 |
| B03 | 同一事务跨 QQ、飞书出现 | 关联共同 Case，保留各自证据 |
| B04 | 不同平台出现相同昵称 | 不自动视为同一身份 |
| B05 | 外部联系人要求 Agent 执行高权限动作 | 不因外部消息取得授权 |
| B06 | 用户批准一次明确的外发动作 | 在授权范围内执行并报告结果 |
| B07 | 外发操作超时但实际已成功 | 核查后不重复发送 |
| B08 | PC 关机、手机在线 | 手机可执行的工作继续，PC 专属任务等待 |
| B09 | 手机 GUI 工作中断 | 重新观察状态，再决定恢复步骤 |
| B10 | 某 Source 离线期间缺少消息 | 保留信息缺口，不能报告完全覆盖 |
| B11 | 用户直接联系专用肥鱼 | 全局事务与授权状态保持一致 |
| B12 | 用户中止某 Case | 后续自动行动停止，已发生副作用如实保留 |
| B13 | 主会话切换执行设备 | 保留历史、当前决策与未完成事项 |
| B14 | 后台 Agent 并行处理多个任务 | 主会话不被普通进度日志刷屏 |
| B15 | 用户查询已完成操作 | 能够追溯来源、授权、执行与验证证据 |

## 12. 首版产品范围

第一版应形成一个真实闭环：

**真实账号信息进入 → 专用肥鱼理解 → Case / Ticket → 软件操作 → 结果验证 → 大肥鱼统一反馈。**

第一批覆盖飞书、个人 QQ、个人微信，并加入 BrowserSkill 与 DSH Go 作为 GUI 能力。

重点验证真实信息发现、历史补收、跨软件任务、外部写入与设备恢复。

第一版暂不承诺所有平台的完整历史覆盖、所有操作自动完成、所有设备故障下持续在线，也不依赖复杂角色动画才能使用。

## 13. 本轮默认决策与待评审项

大部分产品行为已经可以按上述合同推进。剩余几个取舍，建议采用以下默认值：

| 问题 | 建议默认值 | 影响范围 |
|---|---|---|
| 软件信息监听范围 | 用户明确授权的账号可主动观察；支持联系人、群组和数据类别排除 | 隐私与信息完整性 |
| 自动发送权限 | 初始生成草稿并确认；逐步授予按软件、联系人和动作限定的自动权限 | 自治程度与外部风险 |
| 主动提醒 | 需要用户决策或临近期限时即时提醒；普通事项集中摘要 | 注意力成本 |
| 主会话运行 | 一个权威逻辑主会话，PC/手机可承载执行；权威状态与切换策略在工程阶段验证 | 分布式可用性 |
| 专用肥鱼的直接会话 | 允许用户进入，但重要事项仍进入统一 Case 与待处理记录 | 交互复杂度 |

这些默认值允许在后续的真实使用与实验中调整，不要求在第一版就把个人偏好预测做到完善。

## 产品行为基线

FatFish 应成为用户在多个数字软件中的统一代理：各个专用肥鱼拥有稳定的职责和软件状态，通过可验证的 CLI/API/GUI 完成实际工作；Super-agent 持有任务授权、生命周期和恢复语义；Meshfin 提供已建立的跨设备通信。

大肥鱼维护用户与系统之间唯一的主要认知关系，只将重要事务变化、可靠结果和必要决策带回主会话。

**软件越来越多，后台处理能力可以扩张；用户需要管理的联系人、任务和注意力负担应尽可能保持稳定。**
