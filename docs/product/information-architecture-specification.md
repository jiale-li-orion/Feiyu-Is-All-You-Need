# FatFish · 信息架构设计

**Information Architecture Specification**

- 上游依据：Product Behavior Specification
- 设计范围：信息对象、页面拓扑、Attention、通信与上下文边界、状态所有权、导航与验收。

---

## 1. 信息架构目标

FatFish 将多个软件的信息、多个 Agent 的工作以及分布式设备状态统一到一个用户界面。

用户不需要理解 Source、Ticket、Assignment 或 Meshfin 的内部结构，也能够完成主要操作。

信息架构需要支持三种基本意图：

**交流**：联系大肥鱼，提出目标、作出决策、接收结果。

**处理事务**：查看目前有什么需要自己处理，什么已经交给肥鱼，什么正在等待外部条件。

**寻找信息**：跨软件查询消息、联系人、文件、承诺与历史操作，检查原始证据。

系统管理和配置属于低频需求，应通过次级入口访问。

### 核心设计判断

FatFish 的导航以用户意图为主要组织方式。

软件来源、Agent 负责人和执行设备作为对象属性与关联入口，除配置或排障场景外，不成为用户日常导航的第一层。

信息呈现遵循以下顺序：

**当前需要用户知道或决定的内容 → 相关事务 → 来源证据 → Agent 执行细节。**

这种层级同时控制用户需要面对的信息量，以及主 Agent 每次需要读取的上下文范围。

## 2. 概念与信息对象

### 2.1 四种需要严格区分的对象

**FatFish 会话**：用户与大肥鱼或专用肥鱼的 Agent-Human 通讯历史。主会话在逻辑上唯一且持续存在。

**外部会话**：QQ、微信、飞书等软件中的真实聊天、群组、频道和话题。它们是数据来源，不自动成为 FatFish 的用户侧会话。

**Case（事项）**：一个持续存在的用户目标或待跟进事务，可以跨多个软件与外部会话。

**Ticket（任务）**：Super-agent 持有的具体授权工作。一个 Case 可以关联多个 Ticket；简单的一次性执行也可以没有长期 Case。

四者可以互相引用。

一个 QQ 群里的消息可以服务于不同 Case；一个 Case 可以涉及多个软件；一个长期 Case 可以包含多个 Ticket。上述关联只在具体工作需要时建立，无须预先整理所有聊天历史。

### 2.2 信息对象目录

| 对象 | 用户可感知的含义 | 主要关联 |
|---|---|---|
| Main Session | 与大肥鱼的长期对话 | Case、Agent |
| Agent Dialogue | 与专用或通用肥鱼的对话 | Agent、Case |
| Case | 一件需要持续跟进的事情 | Ticket、相关消息与资料 |
| Ticket | 一项具体授权工作 | Case、Mandate、Assignment |
| Attention Item | 当前等待用户关注或处理的内容 | Case、Ticket、异常 |
| External Conversation | 外部软件中的聊天或话题 | Account、External Event |
| External Event | 消息、通知或外部状态变化 | Source、相关会话 |
| Evidence Reference | 原始信息的访问引用 | Event、文件、外部链接 |
| Agent | 负责某个软件或领域的肥鱼 | Source、Capability |
| Software Account | 用户授权接入的软件账号 | Source、Provider、Permissions |
| Person | 某个联系人及其可能关联的平台身份 | Account、Case |
| Device | PC、Android 或其他执行节点 | Capability、Assignment |

**上述对象是概念划分，不等于第一版需要实现同等数量的数据库表、服务或管理页面。**

Attention Item 可以利用 Super-agent 现有的关注与授权机制，也可以从已有对象状态形成待处理视图；不能再创建一套独立的任务所有权。

Evidence Reference 可以是原始消息标识、文件位置或 URL，不要求建设专门的证据数据库。

Person 的跨平台关联属于可选能力。第一版不需要统一联系人身份图谱，仅在确有语义需要时建立具体关联。

Agent 是长期职责主体；Source 负责信息输入；Provider 负责读取与操作。一个专用肥鱼可以负责多个账号，并使用多个 Provider。

### 2.3 对象关系与关联成本

主要关系按责任划分：

- Software Account 通过对应 Source 提供外部事件。Event 可能属于某个 External Conversation，也可能是账号、通知或其他软件事件。
- Case 在需要时引用相关 Event、外部会话、文件或 Ticket。没有 Case 的信息仍可直接读取、查询和操作。
- Ticket 由 Super-agent 管理具体工作及其 Assignment。Case 可以引用 Ticket，但不会因此拥有第二套执行生命周期。
- Agent 负责相应软件或领域的能力。执行设备、Provider 和实际模型 Session 可以变化，Agent 的逻辑职责保持稳定。
- 用户需要处理的事项从关联的 Case、Ticket 或实际异常进入待处理视图。展示一条待办不会复制其任务状态。

这些是**可选的逻辑关联关系，不是事件进入系统后必须依次经过的数据转换流水线**。

### 2.4 渐进关联

关联遵循渐进式、按需建立的原则。

普通消息保留原始来源和必要的访问标识即可，不要求预先提取人物、事件、意图、证据或所属 Case。

用户提出查询、肥鱼执行具体工作，或者已有事务发生实际变化时，再根据需要获取上下文并建立关联。

不为页面展示或所谓数据完整性，持续消耗大量 Token 清洗历史、生成关联图、填充语义字段和附加证据标签。避免过度设计的 evidence-grounded 工作流。

不同平台身份尚不确定时，可以暂时保持独立；存在错误关联时应能纠正。确实合并 Case 时，保留原有任务和重要历史，不丢失相关内容。

用户界面优先采用自然短句、自然长句和自然段式表达。结构化字段只服务于明确的分类、操作和状态需求，不把后台数据模型直接映射成大量表单。

## 3. 全局页面拓扑

### 3.1 一级导航

第一版保持三个主要导航区域：

| 一级入口 | 解决的用户问题 | 主要信息 |
|---|---|---|
| 消息 | 我要跟肥鱼交流 | 大肥鱼主会话、专用肥鱼、重要通知 |
| 事项 | 现在有什么事需要处理 | Case、待确认、执行结果、等待事项 |
| 我的 | 软件和设备如何管理 | 账号、权限、Agent、设备、设置 |

**不需要单独向用户暴露搜索接口，也不需要单独设计全局聚合搜索接口，用户通过自然语言向肥鱼提出查询。非必要的传统软件习惯带来的导航，属于过度设计。**

### 3.2 页面树

第一版确定以下导航层级。

**消息**

- 大肥鱼主会话（默认入口，首页的首屏展示后续单独设计）。
- 会话目录
  - 大肥鱼：始终置顶。
  - 通用肥鱼：始终位于大肥鱼之后。
  - 专用肥鱼：按照最近真实交互时间排序。
- 根据当前对话按需打开的外部消息、文件或结果。

**事项**

- 待我处理：优先呈现。
- 正在推进：包括执行中、等待外部及暂时阻塞。
- 历史：次级入口。
- 事项详情：根据当前问题按需查看相关资料、任务与执行记录。

**我的**

- 个性化与记忆
- 软件连接与权限
- 自动化与通知
- 肥鱼小队与设备
- 外观、数据与隐私
- 后台与开发者

后台与开发者按需进入以下管理领域：

- 运行概览
- 自动化与任务
- Source、设备与执行环境
- Agent、模型与工具
- 资源用量与限制
- 凭据与高级诊断

这些是管理职责分类，不要求每一类都对应一个独立页面。没有独立操作需求的内容可以合并呈现。

第一版不另外设置搜索中心、外部聊天聚合首页、Agent 拓扑首页和实时系统监控首页。

### 3.3 默认进入与导航优先级

导航规则按以下顺序处理：

1. 用户通过通知或链接明确打开某个对象时，进入目标对象。
2. 已有可恢复的客户端状态时，恢复此前的页面、滚动位置与草稿。
3. 没有可恢复状态的冷启动，进入大肥鱼主会话。

后台任务变化不主动跳转页面。

第一版本不增加额外悬浮导航。返回、切换和展开使用普通页面导航，具体控件形式在交互设计阶段确定。

### 3.4 页面职责与信息首次出现的位置

三个主要页面具有明确的信息所有权。

**消息负责真实通讯。** 用户向肥鱼提出问题、委派工作、收到实际回复或授权请求时，内容出现在相应会话中。后台普通事件不会自动生成会话消息。

**事项负责持续工作。** 需要用户处理的决定和仍在推进的任务，出现在统一事项视图。即使没有 Agent 主动发送消息，已有任务状态也可以通过事项访问。

**我的负责配置与检查。** 软件、权限、设备、模型和后台运行信息主要从这里进入。正常运行状态不占用聊天和事项首屏。

进一步明确几类后台变化的默认去向：

| 后台发生的变化 | 默认去向 |
|---|---|
| 普通外部消息或软件事件 | 由 Source、专用肥鱼或后台处理，不产生前台内容 |
| 已有任务的普通进度 | 更新所属 Case/Ticket，事项中按需可见 |
| 需要用户授权或决定 | 进入「待我处理」；有实际通讯时也可出现在对应会话 |
| 异步任务完成 | 更新原任务；按发起时的反馈约定决定是否向用户发送结果 |
| Source、设备或 Worker 异常 | 保留在所属后台状态；影响任务时才在相关位置说明 |
| 用户主动查询的结果 | 返回当前提问的肥鱼会话，必要时附来源链接 |

**页面需要显示某项数据，不构成调用 LLM 分析、生成新摘要或建立新 Case 的理由。**

事项和会话可以引用同一个授权或任务状态，但不会复制两份待处理对象，也不因为对象同时出现在两个页面就生成两条通知。

### 3.5 桌面与手机

桌面与手机共享页面树、业务对象和操作语义。

手机优先呈现一个当前内容；桌面可以并列呈现目录、正文和详情。并列展示不会增加新的业务对象或状态。

会话、Case、Ticket 和授权在设备之间共享；滚动位置、当前页面和临时展开状态由各客户端维护。

同一设备的部分界面功能故障，不应迫使其他页面重新加载无关数据。

## 4. 页面内容与管理边界

### 4.1 消息

**会话目录**

大肥鱼、通用肥鱼始终置顶，依次排列。其他专用肥鱼按照最近一次真实 Agent-Human 通讯时间降序排列。

用户向肥鱼发消息、肥鱼向用户发送真实通讯，都更新最近交互时间。

Source 事件、工具调用、Ticket 更新及后台 Agent 通信，不更新会话排序。

会话行展示头像、名称、最近一条真实通讯的原文截断、通讯时间和必要的未读状态。摘要不另行调用模型生成。

未读只表示用户尚未阅读的真实 Agent 通讯。用户在任一设备阅读后，其他设备同步已读状态。未读数量不反映外部软件消息数、后台任务数或 Agent 工作量。

**大肥鱼主会话**

主会话保留连续自然对话、用户委派、实际回复和必要决策请求。

大肥鱼可以直接回答，也可以联系专用肥鱼或通用肥鱼获取信息。用户无需知道后台调用了哪些 Agent。

当大肥鱼向专用肥鱼委派工作时，专用肥鱼的内部回复不自动进入用户会话。大肥鱼负责向用户交付此次请求的最终回答，避免出现多个肥鱼重复回复。

需要持续执行的工作由后台接管。大肥鱼完成任务受理后，可以继续与用户讨论其他内容；普通执行进度不持续插入主会话。

**专用 / 通用肥鱼会话**

用户直接向专用肥鱼委派工作时，默认由该肥鱼在原会话中回复。涉及其他软件时，可以交给后台协调，或联系大肥鱼进行必要的跨领域判断。

通用肥鱼负责兜底能力，由用户或大肥鱼主动唤醒调度。

专用肥鱼可以在确有交互需要时主动向用户发消息。这类消息更新会话排序和未读，但不能把普通后台事件包装成主动通讯。

一次请求默认由**接收用户请求的肥鱼负责交付结果**。后台可以更新事项，其他 Agent 可以参与工作，但不应各自向用户重复发送同一个完成结果。

特殊情况下确实需要另一名肥鱼直接与用户沟通时，才明确移交交互责任。

不同肥鱼的会话历史独立保存，不同步复制到大肥鱼主会话。

**信息在会话中的形式**

普通答案使用自然语言。需要查看外部内容时，提供实际可用的链接或少量必要原文。需要授权时，呈现明确操作对象与可执行决定。

不按后台对象类型生成固定的卡片集合。

### 4.2 事项

事项页首先呈现「待我处理」和「正在推进」，其次提供历史入口。

**待我处理**

仅包括需要用户完成的授权、选择、补充信息或本人操作。普通技术异常、Agent 自己可以恢复的问题，不自动进入这里。

每条记录应直接表达需要用户做什么。有关期限、风险和优先顺序的具体排序策略留给后续 Architecture Design；信息架构只要求用户能够首先找到真正等待自己行动的内容。

用户已经阅读但尚未处理的事项仍然保留。用户从消息或事项中完成决定，其他位置读取到同一处理结果。

当没有待处理事项时，无需为维持版式而保留大量空白占位内容，可以直接呈现正在推进的工作。

**正在推进**

只保留尚有实际目标、需要持续执行、等待或恢复的 Case / Ticket。

默认显示事项已有的标题或目标表述，以及后台可以直接提供的状态和必要结果。**列表加载不得为每个事项重新调用 LLM 生成进度摘要。**

用户置顶或明确关注的事项优先显示。其余使用已有任务状态和更新时间组织，不因为普通 Worker 日志更新而不断改变顺序。

等待外部、执行阻塞和结果待核查属于事务状态；只有下一步确实需要用户参与时，才进入「待我处理」。

一次性查询或操作在完成后直接交付结果，没有必要强行建立长期 Case。

**事项详情**

进入后首先让用户理解目标、当前进展以及下一步。如果正在等待用户作决定，直接呈现决定内容。

优先使用创建任务时已经存在的目标描述，以及执行过程中已经产生的有效结果。

没有现成解释而用户又确实需要理解复杂情况时，才向对应肥鱼请求语义分析。

不固定生成「背景、摘要、证据、过程、风险、下一步」等字段式页面。研究、软件操作和外部联系事务可以保留各自自然的信息组织方式。

用户需要检查历史、原始资料或执行细节时，再向下展开。

事项详情不主动重跑任务，不自动触发故障重试，也不因为缺少某个展示字段而要求模型补全。

### 4.3 「我的」：普通设置

参考 ChatGPT 设置的管理方式，「我的」以个人控制为主，后台诊断与技术资源管理逐层下沉。

**个性化与记忆**

第一版提供可编辑的偏好、长期指令和个性化说明，主要属于 System Prompt 级别的配置能力。

用户可以用自然语言表达希望肥鱼如何交流、协作、记住或避免使用哪些个人信息。

真正的认知记忆系统、长期上下文压缩与恢复策略留待后续独立设计。不提前承诺一个可以全面浏览、编辑模型全部认知状态的设置页面。

会话历史、个性化配置与后台任务状态分开管理。

**软件连接与权限**

首先展示真实软件账号及其可用能力。用户可以查看或修改读取授权、外部写入权限及必要的连接配置。

Provider 是实现能力的一种方式，不需要在普通设置中默认暴露所有技术细节。

软件能够完成某项操作，与系统被授权自动完成该操作，是两个不同条件。

**自动化与通知**

用户可以查看持续运行的自动化，调整已有触发条件、暂停或恢复工作，并管理主动通知的偏好。

任务与自动化使用后台同一套权威状态，不另建普通设置专用的任务数据库。

暂停通知不停止后台工作，关闭设置页面也不停止任务。

**肥鱼小队与设备**

肥鱼小队管理领域职责、对应软件以及进入会话的入口。

设备管理提供 PC、Android 等节点当前可以承担的能力，以及影响实际工作的连接问题。

Agent 逻辑身份、模型运行 Session 与执行设备相互独立。设备离线不导致联系人消失。

**外观、数据与隐私**

管理主题、语言、肥鱼角色表现、数据保留及权限撤销。

角色动画可以关闭或降级，不影响交流、任务和软件操作。

### 4.4 后台与开发者 Dashboard

Dashboard 是后台平台的管理界面。后台持续运行不依赖 Dashboard 窗口或大肥鱼当前是否正在推理。

第一版的后台按照实际管理职责划分：

| 管理领域 | 首先呈现 | 可执行的管理 |
|---|---|---|
| 运行概览 | 对实际工作有影响的异常、待恢复执行 | 进入受影响任务或能力 |
| 自动化与任务 | Trigger、Ticket、等待与执行记录 | 暂停、恢复、取消、检查历史 |
| Source 与设备 | 软件读取覆盖、节点与 GUI 可用能力 | 检查连接、恢复授权与可用能力 |
| Agent、模型与工具 | 肥鱼职责、模型、CLI/Provider | 配置能力与执行方式 |
| 资源与限制 | Token、模型调用、费用和限额 | 查看消耗、设置预算与预警 |
| 凭据与诊断 | 凭据引用、异常、必要日志 | 安全管理、定位故障 |

六个管理领域不意味着六套独立系统或六个必需的页面。优先复用 Super-agent、Meshfin 与已有 Provider 的状态和管理能力。

Dashboard 默认直接读取确定性信息。用户主动请求解释运行问题或优化配置时，才调用 LLM。

普通设置与 Dashboard 不重复持有授权、任务和设备状态。

参考 OpenAI Platform 的管理边界，但第一版不引入没有真实需求的多租户 Organization、多 Project 和 Service Account 等体系。

### 4.5 外部信息的查看

用户向肥鱼查询外部消息、文件或记录时，系统优先完成必要读取，并在原会话中给出答案。

少量文本可以直接展示；复杂文件、大量历史或外部对象积极提供可用链接，复用已有预览与打开能力。

不为每种外部内容格式设计独立的查看器或复杂的内容调度系统。

**提供链接是为了让用户继续查看或核查，不意味着要求用户亲自打开原软件完成本应由肥鱼执行的任务。**

用户仍可以继续让肥鱼读取链接内容、分析历史或执行已授权操作。

外部内容无法获取时，保留现有结果，并在影响当前问题时明确说明限制。

## 5. 通信、Attention 与 Context

本节确定各主体可以如何交流、哪些信息需要进入前台，以及后台信息和认知上下文如何分离。

Attention 在这里表示信息与工作对不同主体的关注价值。具体评分、排序和调度算法属于后续 Architecture Design。

### 5.1 通信拓扑

**直接语义通信**发生在用户与肥鱼之间，以及大肥鱼与专用肥鱼、通用肥鱼之间。

直接通信表示两端可以围绕当前意图直接交换问题、结论和必要上下文，保留连续推理能力。

它是语义交互关系，**不要求物理点对点网络连接，也不要求绕开后台或重新实现一套传输协议**。实际跨设备通信继续复用 Meshfin 与现有运行能力。

**间接后台通信**负责 Source 事件、自动化触发、任务交接、设备状态与执行结果，通过已有 Super-agent 的任务机制协调。

专用肥鱼之间的普通工作交接优先由后台任务完成。确实需要联合语义分析时，再由大肥鱼按当前目标协调直接交流。

直接交流产生持久任务后，工作由后台持有。Session 可以结束，而任务继续存在。

### 5.2 信息向上呈现的边界

信息可以在后台、领域 Agent、大肥鱼与用户之间流动，但不要求每条事件都经过所有层次。

| 参与主体 | 主要需要处理的信息 |
|---|---|
| 后台 | 原始事件、确定性规则、任务状态、自动化和执行恢复 |
| 专用肥鱼 | 自己领域内需要语义理解或操作的信息 |
| 大肥鱼 | 用户当前意图、跨领域协调、重要的全局目标与判断变化 |
| 用户 | 实际通讯、必要决策、明确需要关注的结果 |

后台可以处理大量事件并推进任务，而不向大肥鱼发送等量消息。

专用肥鱼可以维护自己的领域信息，不要求大肥鱼同步理解全部过程。

大肥鱼收到有价值的信息，也不一定需要即时打断用户。

某个信息是否应提升到更高层次，以及何时处理，后续可以利用搜广推、策略学习和资源约束等方法研究；现阶段不引入独立的 Attention 排序服务或评分公式。

### 5.3 后台信息、领域上下文与全局认知

**后台持久信息**包括软件事件、同步状态、任务授权、执行记录和必要历史。它承担存储、自动化与恢复。

**领域上下文**属于对应专用肥鱼，包括当前领域问题、重要判断和必要历史。具体 Session 可以按需恢复与释放。

**全局认知**属于大肥鱼，主要维护用户的长期目标、重要关系、持续问题和判断演化。

后台保存一条事件，不意味着这条信息应当进入大肥鱼上下文。

领域肥鱼对某个事件形成理解，也不要求立即同步给大肥鱼。

当用户提出相关意图，或者某项信息确实改变重要的全局问题时，大肥鱼再与相关肥鱼交流或按需读取后台资料。

真正的长期记忆算法及上下文压缩、恢复策略后续单独设计。当前信息架构只要求三类信息能够保持不同的生命周期和访问边界。

### 5.4 任务状态与认知更新

普通任务状态由后台权威机制更新。

例如 Ticket 从执行中进入等待，事项页可以直接显示已有状态；无需让大肥鱼重新生成说明。

涉及用户目标变化、长期判断修正或跨领域理解时，才可能需要大肥鱼进行新的语义推理。

因此，**页面数据读取不会自动触发认知更新，任务状态变化不会自动生成新会话，后台历史不会自动成为全局记忆。**

### 5.5 失败与降级

某个专用肥鱼不可用时，其已保存的信息与任务状态仍按实际可用范围提供；新的语义工作可以等待恢复。

大肥鱼暂时没有活跃 Session 时，已经授权的确定性后台工作和独立领域工作可以继续运行。

单个 Source 离线不会阻塞不依赖该 Source 的工作。

任何外部写入发生超时或断连时，优先核查真实执行结果，不能未经检查就重试可能重复生效的动作。

## 6. 状态所有权与导航契约

### 6.1 权威状态

| 信息 | 权威归属 | 页面如何获取 |
|---|---|---|
| FatFish 会话 | 对应会话记录 | 会话目录和对话页面读取 |
| 外部消息及同步覆盖 | Source / Provider | 专用肥鱼或按需查询读取 |
| Case | 后台持久事务记录或既有任务关联 | 事项页读取，主会话按需引用 |
| Ticket、Mandate、Assignment | Super-agent | 事项、会话及 Dashboard 共享状态 |
| 设备能力 | Meshfin / Device Registry | 调度与设备管理读取 |
| Agent 职责与模型配置 | Agent 管理配置 | 会话目录和后台管理读取 |
| 个性化偏好 | 对应用户配置 | 肥鱼在需要时加载 |

这里的权威归属是**逻辑责任边界**，不意味着必须分别建设数据库、微服务或缓存集群。

Case 可根据实际持续事务需要保存必要记录，也可以利用 Super-agent 现有的任务关联能力；不预先假定存在独立 Case Store。

Ticket 的执行、授权与恢复仍由 Super-agent 持有，避免 UI 和业务模块再次实现同一套生命周期。

跨模块传递必要标识与信息，进一步内容按需从原始归属处取得。

### 6.2 显示状态

界面中需要区分：

**会话未读**：用户尚未阅读的真实肥鱼通讯。

**待我处理**：下一步需要用户决定或操作，阅读不会自动解除。

**正在推进**：仍有实际目标的持续工作，包括执行和等待。

**任务完成**：对应目标已满足，必要的外部结果已核查。

**信息覆盖**：某个软件在指定范围内能够提供哪些消息及历史。

这些状态各自具有不同含义，不通过一个通用「在线 / 完成 / 未读」字段混合表达。

### 6.3 导航与返回

业务对象具有稳定标识，页面之间只有在当前交互需要时建立引用。

从主会话打开任务或外部文件，关闭后回到原来的会话位置；从事项进入执行记录，返回仍然停留在原事项。

业务状态跨设备共享，临时导航与阅读状态由当前客户端独立维护。

后台数据更新不会自动切换用户当前页面。

### 6.4 页面独立与故障隔离

消息页不依赖所有 Source 在线；事项页不需要读取全部原始聊天才能展示已有任务；Dashboard 的确定性数据访问不依赖 LLM。

单个模块异常只影响实际依赖它的内容。

已有数据可以继续显示，但需要区分最后确认的状态与当前尚未同步的状态。

高内聚、低耦合首先约束对象职责、依赖方向、读写权限和故障影响范围；具体进程、数据库与服务拆分留给架构设计。

## 7. 验收与阶段边界

这一轮验收页面和信息对象是否具有清晰职责、信息是否出现在正确位置，以及是否存在不必要的语义计算和模块依赖。

| 编号 | 测试情形 | 判定标准 |
|---|---|---|
| IA01 | QQ 收到大量普通群消息 | 不生成等量 FatFish 未读、Case 或用户通知 |
| IA02 | QQ 肥鱼向用户发送一条真实通讯 | 专用肥鱼按最近交互时间移动；大肥鱼和通用肥鱼仍置顶 |
| IA03 | 打开会话目录 | 最近通讯摘要直接截断原文，不触发 LLM 摘要任务 |
| IA04 | 用户询问过去的 QQ 文件 | 在原会话回答，必要时附链接；不要求先创建 Case |
| IA05 | 用户继续追问查询结果中的第二项 | 保留当前指代，无须进入额外搜索界面 |
| IA06 | 用户直接委派 QQ 肥鱼完成一项工作 | 默认由 QQ 肥鱼交付结果，不让大肥鱼重复回复 |
| IA07 | 用户委派大肥鱼进行跨软件工作 | 大肥鱼协调专用肥鱼并向用户回答，后台普通结果不重复推送 |
| IA08 | 一个任务需要等待两天 | 后台继续持有任务，Agent Session 和 Dashboard 可以关闭 |
| IA09 | 打开事项列表 | 使用已有目标和任务状态，不逐项调用模型生成摘要 |
| IA10 | 用户从专用肥鱼会话批准发送操作 | 事项及 Dashboard 更新同一授权状态，不新增重复待办 |
| IA11 | 用户打开某项任务详情 | 不自动启动工具、补齐字段、重新整理全部历史或重试失败动作 |
| IA12 | 用户请求检查某项历史证据 | 按需读取原文，优先复用现有链接与查看能力 |
| IA13 | Windows 微信 Source 离线 | QQ、飞书及主会话的无关能力继续使用 |
| IA14 | 用户询问离线期间的微信消息 | 明确当前读取范围，并尝试可用的补查路径 |
| IA15 | 设备断连导致发送结果不确定 | 保留待核查状态，不盲目重复外发 |
| IA16 | PC 与手机同时查看任务 | 业务状态共享，页面位置互不抢占 |
| IA17 | 用户查看模型费用 | Dashboard 直接读取已有用量，不启动大肥鱼推理 |
| IA18 | 用户编辑个性化偏好 | 更新对应配置，不要求第一版同步实现完整认知记忆系统 |
| IA19 | 用户暂停后台自动化 | 任务后续执行受控，既有历史和相关事务保持可访问 |
| IA20 | 用户关闭 Dashboard | 后台不依赖 Dashboard 页面而停止运行 |

至此，FatFish 的信息架构由三个用户界面领域、一套后台管理载体、两类 Agent 通信路径和清晰的状态所有权组成。软件数量、Agent 数量与外部事件数量的增长，应主要由后台和领域 Agent 承担；大肥鱼保持全局认知连续性，用户只接触有实际交流或决策价值的信息。
